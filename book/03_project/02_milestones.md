## Why milestones matter

Milestones help you see whether your project is developing at a realistic pace. They turn the semester schedule into concrete project checkpoints.

SDS320 is project-driven. The final report, repository and presentations are easier to prepare when you build the project gradually instead of trying to assemble everything shortly before the deadline.

Milestones are practical signals that help you detect delays early.

## Key assessment moments

### Concept presentations

The concept presentation focuses on your project plan. It should explain your motivation, research question, planned data sources, intended methods, expected output and possible bottlenecks.

The goal is feedback early enough to improve the project before most implementation work is completed.

### Final presentations

The final presentation focuses on what you actually implemented, found and learned. It should present your workflow, key results, figures or maps, interpretation, limitations and remaining challenges.

It should also explain how the project changed compared with the initial concept.

### Final project submission

The final project report and repository contribute to the assessed project component. The report must be submitted as a PDF via the corresponding MS Teams assignment by **Monday, 14 December 2026, at 17:00**.

The report must include a link to your public GitHub or GitLab repository.

## How to use milestones flexibly

Not all projects progress at exactly the same speed. Some projects need more time for data acquisition. Others quickly produce outputs but require more work on evaluation or interpretation.

Use the milestone table as a delay detector. When you fall behind, do not simply work faster. Reduce scope, clarify the next decision and ask for feedback.

Good scope reductions include:

- smaller study area,
- shorter time period,
- fewer classes,
- fewer input datasets,
- simpler baseline method,
- one clear output instead of several outputs.

## Red flags

Watch for these warning signs:

| Red flag | First check |
| --- | --- |
| No clear research question after Week 2 | Return to [Research question](03_research-question.md) and narrow the topic. |
| No candidate dataset by the concept presentation | Prioritise data access before method complexity. |
| Data exist but cannot be opened or inspected | Test a smaller sample and ask for help with format, path or environment issues. |
| No working prototype by the data analysis phase | Reduce the study area, use fewer files or simplify the first method. |
| Figures are only created at the very end | Create rough figures early, even if they are not final. |
| Repository is not updated until submission week | Start the README and folder structure now. |
| Project story is unclear after first outputs | Write the five-sentence project story and check whether the output answers the question. |

## Key takeaways

- Milestones help you detect project delays early.
- Concept presentations should happen while there is still time to change direction.
- Final presentations should show implementation, not only plans.
- The final submission requires a PDF report and a public repository link.
- Continuous progress is safer than late project assembly.
